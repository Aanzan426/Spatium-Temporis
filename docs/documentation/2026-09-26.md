## 2. Decisions made

### 2.1 Persistence is driven by the event log, not by the mutators

`SqliteStore` extends `MemoryStore` and overrides one protected hook, `persist(events)`,
which writes rows out of each event's `after` payload inside a transaction.

The alternative — every mutator writing both its row and its event — is the obvious
shape and it makes §5.3 a rule someone has to remember. One forgotten `appendEvent` is
silent, permanent, and invisible until the log is the only copy left. Driving
persistence *from* the log makes an unlogged write structurally impossible: it would
also be an unpersisted write, which fails immediately and loudly. It also means the
payloads' replayability (§5.4) is exercised continuously rather than annually, because
the database is literally reconstructed from them on every write.

Cost: `writeTarget()` in `SqliteStore` and `applyOne()` in `events.ts` are the same
dispatch written twice, one against SQL and one against Maps. They are commented as a
pair. If a target is added to one and not the other, replay and the database disagree,
which is the worst bug this codebase can have — `store-check.ts` asserts they match.

### 2.2 The app writes `.xlsx` with no library

SPEC §5 says the app itself never imports `exceljs`. That left a gap: the app has to
produce the curation workbook (§11), and something has to write the file.

An `.xlsx` is a zip of XML. `zip.ts` is 143 lines and writes **stored** (uncompressed)
entries — legal, universally readable, and it avoids pulling in `pako` or a
`CompressionStream` dance for six small XML parts. `xlsx.ts` writes the sheets with
`t="inlineStr"` cells and a single text (`numFmt 49`) style, which satisfies SPEC §3.1
by construction: there is no code path that can emit a date cell.

Verified the hard way rather than by inspection — `roundtrip.ts` has `exceljs` read back
a file this writer produced, which is the only evidence that matters.

Every zip entry gets a fixed DOS timestamp (1980-01-01). Determinism was free here, and
§16.3 of day 1 is the reason it was taken.

### 2.3 The first revision window reaches back past its own revision

A revision window is the interval between two consecutive revisions (§9) — which leaves
everything *before* the first revision owned by no window, and therefore never exported.
Those are the oldest blocks, the ones that can never be recreated.

`buildWorkbook` clamps window 0 back to the earliest occurrence. One line, and it stops
the export silently beginning at whenever someone first pressed "mark revision".

### 2.4 The migration SQL is injected, not imported

`SqliteStore.open(db, migrationSql)`. The first draft used Vite's
`import sql from './001_init.sql?raw'`, which is a bundler feature: the class was then
unrunnable outside a Vite build, and the schema's first-ever execution would have been in
a browser, by hand, months from now. Passing it in costs one argument and made
`store-check.ts` possible.

### 2.5 Reads come from an in-memory mirror

`SqliteStore` loads every table on open and answers reads from Maps. Not a second source
of truth — it is derived, rebuilt from SQL on every open, and only ever written through a
mutation that has already been persisted. The timeline re-queries the visible range while
panning and every wasm-SQLite query re-marshals rows across the JS boundary; at personal
scale the whole dataset is a few MB. `verifyMirror()` re-reads and compares, and
`store-check.ts` runs it.

### 2.6 DOM for the fold grid, canvas for the timeline

Not a contradiction of §6. The rule was "canvas where the element count is unbounded":
the timeline draws thousands of ticks at arbitrary positions, a week fold is a few dozen
boxes on a fixed grid. CSS grid brings focus, hit-testing and text selection for free.

### 2.7 Projected blocks are hatched, not faded

"Generated from the rule" is a different *kind* of thing from "this happened". A
difference in opacity alone reads as a difference in importance, which is the wrong
claim. Diagonal hatching says "provisional" without spending any of the colour budget
(§9), since hue is already committed to category.

## 3. Decisions reversed

### 3.1 The vocabularies lived in `workbook-layout.ts` — moved to `core/types.ts`

`MAGNITUDES`, `PRECISIONS` and `OUTCOMES` were declared in `src/export/workbook-layout.ts`
on day 1. They are domain vocabulary, and `src/core` may never import from `src/export`
— so the model would have had to declare them a second time, which is exactly the drift
invariant 10 exists to prevent: the workbook would have kept validating against a list
the app had already moved past.

They now live in `core/types.ts` and `workbook-layout.ts` re-exports them. Public surface
unchanged; every existing import still works.

### 3.2 `buildWorkbook(tz)` was treated as a conversion — it is a label

The first run of `roundtrip.ts` failed with all 16 rows mismatched. Cause: the exporter
renders dates with the machine's local calendar (date-fns), but the test passed
`tz: 'Asia/Kolkata'` while the process ran in UTC. The workbook then contained UTC dates
*labelled* `Asia/Kolkata`, and the reader rejoined every row 5h30m off.

This is SPEC §3.2's failure in its most dangerous form — it would have been invisible in
the workbook, produced no error anywhere, and shown up months later as training data
that was systematically wrong about what time things happened.

Corrected in two places: the `tz` option is now documented as naming the zone the dates
were rendered in (it does not convert into it), and `roundtrip.ts` reads the process's
actual zone rather than hardcoding one. `npm run check:roundtrip` sets
`TZ=Asia/Kolkata` so the round trip is exercised in a non-UTC zone rather than in the one
where the bug hides.

### 3.3 The broken fixture's ids were 25 characters

`GOOD_ID` produced 25-char ids, so every row in the deliberately-broken fixture failed
the ULID check first and masked the five other faults — the duplicate-id and
bad-date-format checks both reported "not caught", and "a clean row survives" reported
0 rows kept. A fixture whose faults are the wrong faults is worse than no fixture. The
helper now throws if the id is not exactly 26 characters.

## 5. Concepts introduced

### 5.1 `useSyncExternalStore`, and the selector that loops forever

React's own answer to "an external mutable thing changed". It takes a subscribe function
and a `getSnapshot`, and calls the latter on every render to decide whether to re-render.

The trap: `getSnapshot` must be referentially stable between actual changes. A selector
like `() => store.listNodes()` builds a new array every call, so React sees a change on
every render and loops forever. `useQuery` in `store/useStore.ts` subscribes to the
store's *version number* — a primitive — and derives the array in a `useMemo` keyed on
it.

### 5.2 Interval partitioning, and why greedy lane packing is optimal

Bars are packed into lanes by taking the first lane whose last bar has ended. That looks
like a heuristic and is not: sorted by start time, left-to-right greedy uses the minimum
possible number of lanes for a set of intervals. It is the known answer to interval
partitioning, not an approximation of it.

### 5.3 Passive wheel listeners

React attaches `onWheel` passively, which means `preventDefault()` inside it is ignored
and ctrl+scroll zooms the whole browser page instead of the timeline. The fix is a
manual `addEventListener('wheel', handler, { passive: false })` in an effect. This is
one of the few places where dropping out of React's event system is necessary rather
than merely convenient.

### 5.4 `Intl.DateTimeFormat` as a timezone database

`_meta.tz` is an arbitrary IANA name from the workbook, not the machine's zone, so
date-fns alone cannot convert with it and the machine's own offset is wrong by
definition. `Intl.DateTimeFormat` carries the full tz database and is already in Node:
format the instant in the target zone, re-assemble the reading as if it were UTC, take
the difference. That is `zoneOffsetMs` in `tools/xlsx-to-jsonl/tz.ts`, and it is
dependency-free.

Two passes are needed, not one. The offset depends on the instant, and the instant is
what is being solved for — so pass one uses the offset at the naive guess and pass two
re-checks it at the answer. They differ only near a DST transition, which is exactly
where a single-pass version is wrong.

`hourCycle: 'h23'` and not `hour12: false`: the latter returns hour "24" for midnight in
several Node versions, and 24 quietly becomes the next day.

### 5.5 `node:sqlite`

Node 22 ships SQLite in core. No npm package, no native build, no wasm — which is what
makes running the real `001_init.sql` in a verification script cheap enough to do on
every change. It is a scripts-only dependency: it does not exist in a browser, so the
app never imports the adapter.

## 6. Open questions

DESIGN §12's five are all still open and none of them blocked anything today. Two of
them now have a provisional answer in code that should be made explicit or reversed:

- **Sections on types or on nodes?** `NodeType.sections` exists; nodes carry free
  `attrs`. That is "both", by default rather than by decision.
- **Inbox ordering beyond recency?** Currently recency only, sorted by ULID with no extra
  column.

New, from building it:

- `blocksInRange` merges materialized and projected on every call. At a decade of daily
  rules that is ~3,650 projections per query. Fine now; the fix, when it stops being
  fine, is a cache keyed on `(rule, range)` rather than a different design.
- `App.tsx` seeds a `MemoryStore` on every load. Swapping in `SqliteStore` needs sql.js
  installed and the wasm binary copied into `public/` — three lines, deliberately not
  done today because it cannot be verified in this environment.
