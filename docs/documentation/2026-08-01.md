## 1. What the project is

Established up front, because it changes every downstream decision: **this is not a task
manager.** It is a place to externalise an entire mind — projects, goals, books, workouts,
finance, dreams, long-shot ideas — and see it laid out across time.

The operative requirement, from which everything else follows:

> **The gap between a thought existing in the head and existing on screen must be near zero.**

If capture takes thirty seconds of deciding *where a thing goes*, the tool gets abandoned
inside a week. Every decision below is downstream of that number.

Stated motivation, recorded because it is load-bearing on the design and not derivable from
the code: two-plus years of maladaptive daydreaming produced an unusually large capacity for
constructing and holding elaborate multi-year plans, with no external surface to put them on.
The app exists to be that surface. This is *why* capture latency outranks every other
requirement, and why "the app must not contain my mind" is a real constraint rather than a
slogan.

## 2. Core design decisions

Chronological. Each one records what it replaced and why.

### 2.1 Everything is a node

**Decision.** There is no `Task` table, no `Book` table, no `Workout` table. There is a
`node`, an `edge`, a `span` and an `event`. A book is a node. A workout split is a node.
"Arms" is a node linked to it. An application to rtCamp is a node with a span. Anthropic is
a node.

**Why.** Every domain named — books, workouts, quant study, Stanford, IIM, CFA, cars,
watches, dreams, patents, Capcom, Anthropic — has identical structure: a thing, with a type,
some attributes, some links, and optionally an extent in time. Writing per-domain tables
means a code change every time a new area of life appears. Writing one generic model means
adding "watches I want to buy" is a *user action at runtime*.

**Consequence.** Adding a domain never requires a commit. This was identified as the single
highest-leverage decision in the project, and one that costs nothing on day one and is
extremely expensive to retrofit.

### 2.2 Fixed tiny core, dynamic everything above it

**Decision.** Exactly four hardcoded concepts, forever: `node`, `edge`, `span`, `event`.
Everything else — node types, section templates, relation names, statuses, colours,
categories — is data created at runtime.

**Why.** This was a direct pushback on the stated requirement of "no hardcoded nor hard set
vars." Taken literally, that produces a system so generic it has no opinions, which is the
wall Notion, Tana and Roam all hit — fully schemaless systems become mush; fully rigid ones
become cages. The line between them is a small fixed skeleton with unlimited dynamic flesh.

**Outcome.** Accepted. Recorded as `DESIGN.md` §2.

### 2.3 Precision on every span endpoint

**Decision.** Every span endpoint carries a precision:
`exact | hour | day | week | month | quarter | year | decade | someday`.

**Why.** "3:00–4:30 gym today", "Stanford, sometime after postgrad" and "IIM or quants,
undecided, ~2028" are all spans. Storing them identically forces the UI to lie about how
committed each one is. With precision, a 3pm meeting renders as a hard-edged bar and a
decade goal renders as a soft gradient that fades at both ends.

**Why it matters specifically here.** The plans change constantly and by admission. Precision
is what lets the system absorb that instead of fighting it, and it makes the ratio of
committed to speculative *visible* without the app editorialising about it.

Recorded as `DESIGN.md` §3.

### 2.4 Magnitude is the zoom filter

**Decision.** Every node carries a magnitude: `micro | kilo | mega | giga | tera`. Zoom level
selects which magnitudes render.

- Day zoom → micro + kilo (today's actual work)
- Month zoom → micro dissolves, kilo + mega render
- Decade zoom → only tera; four or five bright threads across a whole life

**Why.** This came directly out of the phrase "mini micro kilo mega giga terra goals" — read
as a real field rather than a figure of speech. Without it, every zoom level renders every
node; at the expected volume (thousands within a year) the view becomes noise and the tool
dies. With it, legibility at every scale is automatic and requires no configuration, because
one gesture moves through time *and* significance simultaneously.

**Side effect.** A tera-goal and a 20-minute errand can coexist without competing for
attention — they never render at the same zoom.

Recorded as `DESIGN.md` §4.

### 2.5 Capture is never gated on classification

**Decision.** `type`, `span` and links are all nullable. A node with only a title and a
timestamp is completely valid. The app must never ask "which project is this?" before
accepting input.

**Why.** Direct consequence of §1. The moment the app requires a category before it accepts a
thought, it becomes a container — the exact thing it exists not to be.

**Scope change caused.** Added an **inbox rail** to Phase 1 that was not in the original
Phase 1 description. Undated capture lands with `span = null` and sits beside the timeline
until it earns a date. Cost: one UI strip, because spans were already nullable.

### 2.6 Nothing is deleted

**Decision.** No pruning prompts, no staleness nagging. Abandoned branches dim; they do not
disappear. A long-shot idea costs one row and does not have to be plausible, scheduled or
connected to anything.

### 2.7 Append-only event log, from commit one

**Decision.** Every mutation appends to `events`. Normal mutable tables are kept for reads —
this is *not* full event sourcing, which would be overkill for a prototype. Roughly 20 lines
of code alongside every write.

**Why.** The eventual goal is fine-tuning a local model into an apprentice. **Current state
is nearly worthless as training data** — a snapshot of tasks teaches a model nothing about
how a person thinks. The signal is entirely in the *changes*: how plans get re-cut, what
links to what, what gets abandoned and when.

**Why it had to be decided today.** A year of unrecorded decision history cannot be
recovered. This is the only Phase 1 decision driven purely by Phase 4.

### 2.8 Event payloads must be replayable

**Decision.**

```
BAD    { kind: 'span_changed', node_id: 'x' }
GOOD   { kind: 'span_changed', node_id: 'x',
         before: { start_ms, end_ms }, after: { start_ms, end_ms } }
```

**Why.** A payload naming only *what* changed records nothing usable. March 3rd cannot be
reconstructed from it, and the training corpus is empty of signal. One write with
`{before, after}` buys revision replay, undo, and an explicit delta for training
simultaneously.

**Failure mode.** Invisible until the day the data is needed and isn't there. Added as
non-negotiable §5.4 specifically because it looks harmless while being written.

### 2.9 ULIDs, never autoincrement

**Decision.** Every id is a ULID.

**Why.** Two devices writing one dataset with integer ids collide the instant sync exists.
Free today, unfixable later. ULIDs are also lexicographically sortable by creation time,
which gives ordering for free.

### 2.10 UTC epoch milliseconds stored, local time rendered

**Decision.** All timestamps are `INTEGER` UTC epoch ms. Rendering converts to local. All
date arithmetic goes through `date-fns` via one module (`src/core/time.ts`).

**Why.** DST transitions and variable month lengths break naive arithmetic. `+ 86400000` is
not "a day" twice a year.

### 2.11 Export beats storage engine

**Decision.** Full `.sqlite` + JSON snapshot export on a keyboard shortcut, in Phase 1.

**Why.** Raised in response to a concern about browser storage being fragile. The factual
correction: IndexedDB/OPFS is real on-disk storage, gigabytes, surviving reboots — not
session storage. But for a lifelong personal archive the underlying instinct was still right,
just for a different reason: an opaque browser-managed blob is a bad place to keep ten years
of thinking. The fix is not the storage engine, it is **having a working export**. Backups
beat storage medium.

## 3. Architecture decisions

### 3.1 The timeline is one transform, not eight views

**Decision.**

```
scale = pixels per millisecond
x(t)  = (t - tOrigin) * scale
t(x)  = tOrigin + x / scale
```

The camera is **two numbers**. Zooming changes `scale`; panning changes `tOrigin`. Which zoom
band is active is *derived* from `scale`, never a mode that gets switched.

A band is one row of data: `{ minScale, maxScale, tickGenerator, labelFormat }`. Adding
centuries later is adding a row. Adding seconds is adding a row. No new rendering code, ever.
Bands cross-fade on opacity across their overlap so zoom feels continuous rather than
snapping.

**Why.** The stated requirement — seconds to centuries — implies eight or more views if built
naively, meaning eight implementations and eight sets of bugs. One transform collapses it to
one implementation plus a table.

**Phase 1 registers exactly four bands:** day, week, month, year. Hours and decades/centuries
are deliberately unregistered so the mechanism gets proven before the range is widened.

**Two identified traps:**
1. **Viewport culling.** Compute the first visible tick and step forward. Iterating every day
   between 1900 and 2100 freezes the app the moment you zoom out.
2. **Canvas 2D, not SVG or DOM.** Thousands of ticks and bars will not survive DOM nodes.

### 3.2 Pages are projections

**Decision.** Every page is a projection over the one store. No page ever gets its own tables
or its own copy of the data.

**Phase 1 builds two:**
- **Main page** — answers *when*. Continuous time axis, one-off spans, zoom across scales.
- **Scheduler page** — answers *what does a typical week look like*.

### 3.3 The scheduler is the timeline folded on a period

**Decision.** Week or month is a single parameter — the fold period — not two
implementations. Occurrences generated by the scheduler also render as bars on the main
timeline. Two projections, one dataset.

**Why.** Same principle as §3.1: one mechanism, parameterised. It also prevents the scheduler
becoming a worse copy of the timeline.

### 3.4 Past occurrences frozen, future occurrences generated

**Decision.** Past occurrences are materialized rows in the database. Future occurrences are
generated on the fly from the recurrence rule.

**Why.** Changing "gym Mon/Wed/Fri" to "gym Tue/Thu" must leave last month showing
Mon/Wed/Fri — that is what actually happened. If past occurrences were generated from the
*current* rule, editing a schedule would silently rewrite personal history, and the revision
view would be a liar.

**Failure mode.** Invisible for months, then discovered after it has already corrupted the
record. Promoted to non-negotiable §5.5.

### 3.5 Recurrence: a deliberately tiny subset

**Decision.** Phase 1 supports daily, weekly-on-selected-weekdays, and per-occurrence
exceptions (skip this one, move this one). Nothing else. Field shapes stay RRULE-compatible
so expanding later is not a rewrite, but **no RRULE parser is written**.

**Why.** Full recurrence — "every 2nd Tuesday except holidays", timezone-shifted exceptions —
is a multi-week rabbit hole that has consumed entire calendar projects. The tiny subset
covers roughly 90% of real personal scheduling for roughly 10% of the complexity.

### 3.6 Periods come free

**Decision.** No period table and no period concept. **A period is the interval between two
consecutive revisions.** An optional `label` on a revision names the period it opens.

**Why.** The stated model was "1st–10th = period 1 = schedule 1, 11th–14th = period 2 =
schedule 2". That falls out of the revision list at zero cost — one column implements the
entire feature.

### 3.7 The Store interface is the platform seam

**Decision.** Every read and write goes through one interface (`src/store/Store.ts`). Nothing
above it imports sqlite, IndexedDB, Capacitor or Tauri directly.

**Why.** This is the only thing that makes web → PWA → Android APK → desktop a *swap* rather
than a rewrite.

### 3.8 Platform path

| Stage | Package | Storage |
|---|---|---|
| Now | Web + PWA (installable, offline, phone home screen) | SQLite (wa-sqlite/sql.js) over IndexedDB/OPFS |
| Phase 2 | Capacitor → Android APK, sideloaded | Native SQLite file in app storage |
| Later, optional | Tauri desktop, or Play Store | Native SQLite file; Rust side can host local SLMs |

**Play Store deferred.** Reasoning: the Play Store exists to distribute to strangers, and
this app has exactly one user. A Play Console account, app review, a hosted https origin and
digital asset links buy nothing for an audience of one. A PWA or a sideloaded APK already
puts the app on the device.

**React Native and Flutter rejected** — both mean a second codebase and a full rewrite.

**Tauri deferred rather than rejected.** Tauri v2 covers desktop and Android from the same
Rust core and would eventually let a local SLM run in-process, which matches the Phase 4
goal. It was deferred because GUI toolchain setup on WSL2 (WSLg, Android SDK + NDK, Rust
cross-compilation) is a fight to have *after* there is something worth packaging, not before
the first feature.

### 3.9 Phone captures, desktop structures

**Decision.** One database, two views. Phone view is a text box and a list. Desktop view is
the timeline, the panels, the drag-to-schedule and eventually the graph.

**Why.** Capture wants a phone — thoughts happen while walking, not at a desk. Structuring
wants a desktop — the described 35/65 panels, drag interactions and node graph are unusable
at phone size. This maps exactly onto the capture-versus-structure divide.

## 4. UI decisions

### 4.1 The 3D graph: constrain one axis

**Proposed by the user:** a fully 3D tree built from light rays, free-rotating on all three
axes; alternatively a multiverse of timeline threads converging on the present.

**Assessment given.** The aesthetic instinct and the topology instinct are both right. Free
3D is a trap: force-directed 3D graphs look extraordinary at 40 nodes and become unnavigable
at around 300 — occlusion, depth ambiguity, no stable spatial memory (the node that was "up
and left" has moved), and hit-testing is miserable. At the expected node volume that ceiling
arrives within about two months.

**Recommendation.**

> **X is always time. It never rotates away.**

Y and Z carry semantics (domain, layer, branch). Rotation around the time axis stays
meaningful and the mental map survives. It also makes the timeline and the graph *one space*
sharing an axis, rather than two disconnected panels in a 35/65 split.

**On the aesthetic:** additive blending, bloom, and thin bright lines on near-black gets
roughly 90% of the light-ray look in 2D canvas. Real 3D geometry waits until the data demands
it.

### 4.2 The light cone

**Observation.** The described structure — present as a converging point, future spreading
outward into a multiverse — is a **light cone**, and the repository is already named
*Spatium Temporis* (space-time). Past converges: fixed, collapsed, one history. Future
diverges: branching, possible, dim where uncommitted. Abandoned plan-branches stay in the
cone at low brightness.

This is a principled structure rather than decoration: it encodes "no plan is ever lost"
directly in the geometry. Filed as the eventual main view (`DESIGN.md` §11), deliberately not
built in Phase 1.

### 4.3 Revision comparison — the spec-sheet model

**Requirement.** Menu → dropdown → Revisions → a horizontally scrolling strip of every
revision; every timing change produces a revision; compare up to 7 side by side, the way
phone or car models are compared.

**Final design.** Columns are revisions, rows are slots, cells are contents. Unchanged rows
dim; changed cells are emphasised. Horizontal scroll past ~7 columns. "Mon 6am: gym / gym /
— / run" reads straight across.

**Explicitly rejected: overlaying colored schedules on one grid.** Readable at 2, mushy at 3,
noise at 7 — transparency stacks multiply, so an overlap of three is indistinguishable from
one dark region. There is also a **colour budget conflict**: hue already encodes category, so
a second hue system for "which revision" fights the first. Columns differentiate by
*position*, which costs no colour budget.

**2-way diff** (green/amber/red, a palette reserved and never used for categories) is a fast
follow on the same table, not Phase 1.

### 4.4 The "as of" scrubber

**Decision.** The revision control *is* a time control — drag it back and the grid replays
the event log to that date, rendering read-only and dimmed. No separate history screen; same
mental model as the main timeline.

**Noted as a verification mechanism.** The scrubber is the test for whether the event log was
built correctly. If it cannot reconstruct a past date, the payloads were incomplete
(see §2.8) — and that is discovered *after* the intervening history is already lost.
Mitigation recommended: a throwaway script that replays the whole log and asserts the result
equals current state. Ten minutes of work.

### 4.5 RevisionStrip performance

**Noted for implementation.** Rendering N revision miniatures by replaying the event log
independently per card crawls once N is 7 and the log is months long. Replay **once**,
forward, snapshotting state at each revision boundary as it is passed. One pass, N snapshots,
then draw — the same total work as rendering a single revision.

## 5. Decisions reversed today

The most useful section. All four were reversals of positions I had argued for.

### 5.1 Small multiples → spec-sheet comparison table

**I proposed** small multiples for comparing revisions: 7 miniature week grids in a row,
identical scale, differences caught by eye.

**Corrected to** a spec-sheet comparison table (§4.3), on the argument that phone and car
comparisons are the right reference.

**Why the correction was right.** Small multiples suit *continuous, visual* data. A schedule
is *discrete and enumerable* — a finite set of slots with contents. Enumerable data reads
better as a table with aligned rows than as miniature pictures. My original recommendation
applied the right technique to the wrong data shape.

**Retained from the original:** the revision strip still exists as a scrolling list; the
comparison table is what opens from it.

### 5.2 Coalescing → rejected

**I proposed** collapsing events within a ~5 minute idle window into a single revision card,
expandable to the raw events, to stop the strip filling with hundreds of entries per month.

**Rejected** on the grounds that it fabricates structure and hides what actually happened.

**Resolved by separating two things I had run together:**
- *Coalescing* — merging multiple distinct committed changes into one card. **Dropped.**
- *One revision per committed change, not per input frame* — a two-second drag is a single
  revision on release, not 120 revisions at 60fps. **Kept**, because intermediate drag frames
  were never changes in the first place, and logging them records a mouse moving rather than
  a decision.

This distinction is now written into `DESIGN.md` §9 and `src/store/events.ts`.

### 5.3 Adherence data in Phase 1 → moved to Phase 2

**I argued** that "what did I actually do" (occurrence outcomes: done / skipped / partial /
moved) is unrecoverable if not captured from day one, and is the richest possible training
signal — the gap between planned and enacted.

**Overridden with a better distinction:** a schedule is a **framework** — a structure,
versioned, comparatively stable. Enactment data is volatile and belongs to a different, more
dynamic layer. Framework ships in Phase 1; enactment in Phase 2.

**Why the override holds.** My "unrecoverable" argument was correct in kind but wrong in
magnitude: the only data lost is adherence for the weeks between Phase 1 and Phase 2, which
is bounded and small. The architectural cleanliness of separating framework from enactment is
worth more.

**Mitigation applied:** the `outcome` column exists in the Phase 1 schema regardless, so
Phase 2 needs no migration. Recorded in `001_init.sql` and `DESIGN.md` §9.

### 5.4 Incrementally maintained CSV → generated-on-demand XLSX + a converter

**Proposed:** a CSV updated on every addition, one page per period, sent for processing at
month end.

**Three objections raised:**
1. **CSV has no pages or sheets** — it is one flat table. Sheets are an `.xlsx` feature.
2. **A file kept in sync on every write is a second source of truth** that will drift, and it
   puts sync obligations on every write path. The database already has everything.
3. **JSONL, not CSV, for training** — training pipelines expect one JSON object per line, and
   the data is nested (a schedule has occurrences, which have outcomes and notes). Nesting
   does not flatten into CSV without losing structure or exploding into denormalized
   repetition.

**The decisive argument for generate-on-demand:** the correct export format is unknowable
until a fine-tune has actually been attempted, and it will be rewritten five or six times.
Generated on demand, a format change costs one function and *every past month can be
re-emitted in the new shape*. Maintained incrementally, every previous export is frozen in an
outgrown format — and the earliest months, the ones that can never be recreated, are stuck
worst.

**Resolution reached:** `.xlsx` becomes the **human curation surface** — export, review and
edit by hand, then run `tools/xlsx-to-jsonl` to produce training JSONL. This is a legitimate
loop: the spreadsheet is where a human decides what is worth training on.

**One requirement that makes the round trip work:** every exported row carries its `id`, so
the converter can rejoin to the database and recover the nested structure that flattening to
a grid destroyed. Without it, xlsx → jsonl is lossy in exactly one direction, which is the
worst kind.

### ULID

A 128-bit identifier, rendered as 26 characters. Unlike a UUIDv4 it embeds a millisecond
timestamp in its high bits, so ULIDs sort lexicographically in creation order — sorting
strings gives chronological order for free, and database indexes on them stay dense rather
than fragmenting the way random UUIDs do.

The reason for using one instead of `INTEGER PRIMARY KEY AUTOINCREMENT`: autoincrement ids
are assigned by *the database*, so two devices offline at the same time both allocate id 47
for different rows. On merge they collide, and there is no correct resolution. ULIDs are
generated client-side from randomness plus time, so collision is effectively impossible
without coordination.

### Epoch milliseconds, UTC, and why date arithmetic breaks

"Epoch ms" is the number of milliseconds since 1970-01-01T00:00:00Z. It is an absolute
instant with no timezone attached, which is exactly what you want in storage.

`+ 86400000` is not "one day". On a DST spring-forward day the local day is 23 hours; on
fall-back it is 25. Adding a fixed 86,400,000 ms lands an hour off, twice a year. Months are
worse: adding "a month" to January 31st has no arithmetic definition at all.

This is why all date work goes through one module using `date-fns`, which does the
calendar-aware thing.

JavaScript numbers are IEEE-754 doubles, exact for integers up to 2^53 — about ±285,000 years
in milliseconds. Centuries-scale zoom is nowhere near that limit, so ms arithmetic on the
timeline is safe.

### Local midnight versus a UTC instant

An occurrence's `date_ms` is "the day this belongs to", stored as **local midnight of that
day** — not the UTC instant of its start time.

Get it backwards and a 6am session in a timezone that shifts will compute to the previous
day's date roughly twice a year. The symptom is a handful of scattered entries on the wrong
day, which looks exactly like random corruption and is very hard to trace back to a timezone
bug months later.

### EAV versus a JSON column

**EAV** (entity-attribute-value) stores user-defined fields as one row per attribute:
`(node_id, key, value)`. Fully queryable and indexable, but every read becomes a join and
reassembly.

**JSON column** stores them as one blob per row. SQLite can query inside it with
`json_extract(attrs, '$.author')`.

Chosen: JSON column, because at personal scale (one user, likely under 100k nodes) the query
performance difference is irrelevant and the code is dramatically simpler. Revisit only if it
actually hurts.

### Append-only event log, and why it is not event sourcing

**Event sourcing** proper means the event log is the *only* source of truth — current state
exists solely as a fold over all events, usually with periodic snapshots for speed. It is
powerful and it is a lot of machinery.

What is being built here is lighter: normal mutable tables serve reads, and every write
*additionally* appends to `events`. Reads stay trivial; history is still complete. Roughly 20
lines of extra code.

The log serves three purposes at once: revision history, undo, and the training corpus.

### Replay, and the `{before, after}` requirement

"Replaying to a timestamp" means starting from a known state and applying every event up to
that time to reconstruct what the data looked like then.

This only works if each event carries enough information to be *applied*. `{kind:
'span_changed', node_id: 'x'}` says something moved but not to where — it cannot be applied,
so replay is impossible. `{before, after}` can be applied forwards (replay) and backwards
(undo), and the delta between them is itself the interesting training signal.

### Projection

A read-model derived from underlying data, rather than a separate copy of it. Both pages are
projections: the main timeline and the scheduler render the *same* nodes, spans and
occurrences in different arrangements. Neither owns storage.

The rule "no page gets its own tables" is what prevents the classic failure where two screens
slowly disagree about what the data is.

### Viewport culling

Only compute and draw what is currently visible. For the timeline: derive the first tick
inside the visible time range, then step forward until you exit it — never iterate the full
range and filter afterwards.

Without it, zooming out to a century means generating ~36,500 day ticks to draw perhaps
twelve, on every single frame. It is the most common way this kind of view dies.

### devicePixelRatio

On a high-DPI screen, one CSS pixel is backed by two or three physical pixels.
`window.devicePixelRatio` is that factor.

A canvas has two independent sizes: its CSS display size, and its backing-store size
(`canvas.width`/`canvas.height`). If the backing store is not scaled by the ratio, the browser
upscales a low-resolution bitmap and everything looks soft. The fix is to set the backing
store to `cssSize * dpr` and call `ctx.scale(dpr, dpr)` so drawing coordinates stay in CSS
pixels.

Worth doing on day one, because the symptom — slightly blurry text — reads as a font or
rendering problem rather than a sizing one.

### Canvas 2D versus SVG versus DOM

- **DOM/SVG**: one element per drawn thing. The browser tracks, styles, lays out and
  hit-tests every one. Excellent for tens or hundreds of elements; collapses at thousands.
- **Canvas 2D**: one element, drawn imperatively. No per-item cost, but no free hit-testing
  or accessibility — you compute what is under the cursor yourself.

At the timeline's density (thousands of ticks and bars, redrawn during every pan and zoom
frame) canvas is the only viable option. The rest of the UI stays DOM, where its advantages
are real.

### The affine time transform, and zoom-about-cursor

```
x(t) = (t - tOrigin) * scale
t(x) = tOrigin + x / scale
```

For zoom to feel correct, the instant under the cursor must not move while `scale` changes.
Hold `t(xCursor)` fixed and solve for the new origin:

```
tCursor  = tOrigin + xCursor / scale          // before
tOrigin' = tCursor - xCursor / scale'         // after
```

Zooming without this pins the transform to the left edge, and the content lurches sideways
under the pointer.

### Small multiples

Tufte's term: the same chart drawn repeatedly at small size with identical scales and axes,
varying one variable across the series. It works because the eye compares *positions* across
a fixed frame extremely well.

Applies to continuous or visual data. It was proposed for revision comparison today and
correctly rejected in favour of a table, because schedule slots are discrete and enumerable —
aligned rows of text beat small pictures for that shape (§5.1).

### Colour budget

In any visualization, hue is a finite channel. Once it encodes one variable — here, category
— it cannot simultaneously encode another (which revision) without the two becoming
ambiguous.

The way out is to encode the second variable on a *different* channel: position, in this case
(one column per revision). This is why the diff palette (green/amber/red) is explicitly
reserved and forbidden for categories — it is a third, separate use of the same channel and
has to be walled off deliberately.

### PWA, IndexedDB, OPFS, and storage persistence

A **PWA** is a web app with a manifest and a service worker, which lets a browser install it
to the home screen or app launcher, run it without browser chrome, and work offline.

**IndexedDB** is the browser's transactional on-disk key-value/object database. **OPFS**
(Origin Private File System) is a newer, faster, file-shaped private storage area, which is
what SQLite-in-the-browser builds prefer.

Both are genuinely on disk and survive reboots — they are not session storage or cookies. The
real caveat is *eviction*: under storage pressure a browser may clear them for origins it
considers unimportant. `navigator.storage.persist()` requests exemption from that.

Which still matters less than having a working export.

### wa-sqlite / sql.js

SQLite compiled to WebAssembly so real SQL runs in the browser. `sql.js` is the older,
simpler one (database held in memory, persisted by writing the whole file out). `wa-sqlite`
supports pluggable VFS backends including OPFS, so it can persist incrementally rather than
rewriting everything.

The point of using either: the SQL written today is the same SQL that runs against native
SQLite in a Capacitor APK or a Tauri desktop build later. Only the file behind
`SqliteStore.ts` changes.

### Capacitor, Tauri, TWA

- **Capacitor** wraps an existing web app in a native shell (Android/iOS) and exposes native
  APIs — including a real SQLite plugin backed by a real file. Same codebase, real APK.
- **Tauri** pairs a web frontend with a Rust backend in a small native binary; v2 covers
  mobile too. Attractive later because the Rust side can host a local model process.
- **TWA** (Trusted Web Activity) is an Android wrapper that displays a PWA full-screen from a
  verified origin — the usual route to putting a PWA on the Play Store. Requires a hosted
  https origin and digital asset links.

### JSONL versus CSV versus XLSX

- **CSV** — one flat table, no sheets, no nesting, no types. Fine for a rectangle of values.
- **XLSX** — a real spreadsheet: multiple named sheets, formatting, formulas. This is why
  "one page per period" requires xlsx rather than csv.
- **JSONL** — one JSON object per line. Nesting survives, files stream line by line without
  loading whole, and every fine-tuning pipeline expects this shape.

### Recursive CTE

`WITH RECURSIVE` in SQL: a query that repeatedly feeds its own output back into itself until
nothing new is produced. It is how you walk a graph — "all nodes reachable from X" — in a
relational database.

The reason a dedicated graph database (Neo4j and similar) is unnecessary here: SQLite plus an
`edges` table and a recursive CTE traverses the link structure perfectly well at
single-person scale.

### RRULE

The recurrence rule format from the iCalendar standard (RFC 5545) —
`FREQ=WEEKLY;BYDAY=MO,WE,FR;UNTIL=...`. It is the universal vocabulary for repeating events,
and implementing it fully (BYSETPOS, exception dates, timezone-aware expansion) is a genuinely
large project.

The decision here is to keep the *field shapes* RRULE-shaped — a frequency, a weekday list, a
start, an until — so that adopting a real RRULE library later is a swap rather than a data
migration, while writing none of the machinery now.

### Force-directed graph layout

A physics simulation: edges act as springs pulling connected nodes together, nodes repel each
other, and the system is run until it settles. It produces the familiar organic node-and-line
picture.

Its weakness, and the reason free 3D was argued against: the layout is *emergent*, so it is
not stable. Adding a node re-settles everything, and the spatial memory built up ("that
cluster is over there") is destroyed. In 3D this compounds with occlusion and depth ambiguity.
Fixing one axis to time removes the instability along the axis that is queried most.

### Light cone

From special relativity: for any event in spacetime, the set of points that could have
influenced it (past cone) and the set it could influence (future cone), drawn as two cones
meeting at the present.

The described structure — past converging to a point at the present, future fanning out into
possibilities — is exactly this shape, which is a good reason to build the visual identity on
it rather than on a generic tree. The repository name already refers to it.

## 13. Design decisions after the scaffold

### 13.1 "Period" retired — it meant two different things

It had been used both for *the interval a schedule version holds* and for *a single scheduled
slot*. One word, two meanings, both in the docs.

- **Block** — one start–end slot with a category.
- **Revision window** — the interval between two consecutive revisions.

Swept through `DESIGN.md` and `SPEC.md`; only the note explaining the retirement still uses
the old word.

### 13.2 Blocks and contents — the bracket and what fills it

A schedule is a day's blocks: start, end, category. **It needs no new tables** — a block *is*
an `occurrences` row, and a category *is* a user-defined node type.

What happened *inside* a block — which book, how many pages, which route, that a language app
got used during a commute — is separate. The tempting shortcut is a `contents` JSON column;
one example kills it: a language session done during a travel block belongs to the travel
block **and** to the language-learning goal. Nested inside the block it is trapped there,
invisible to "how much of this have I actually done."

**Contents are ordinary nodes joined by edges.** One block holds many; one content node sits
in many contexts. That is the work the graph exists to do.

### 13.3 The end-of-block alarm is infrastructure, not convenience

Nobody fills in a week of outcomes on Sunday honestly — they reconstruct, and reconstruction
is fiction. A prompt at the moment a block ends, answered in two seconds, is the difference
between a real adherence record and an invented one.

Red asks two follow-ups: **why** (`reason`) and **what now** — and "what now" creates a *node*
with an edge back to the failed occurrence, not a text field. That yields causal chains
(*when this gets missed, this is what happens next*), a far stronger training target than
prose.

### 13.4 Schema additions

`occurrences` gained `reason TEXT` and `follow_up_node_id TEXT REFERENCES nodes(id)`. Both are
Phase 1 *columns* with Phase 2 *UI* — same call as `outcome`, so no migration is ever needed.

## 18. Concepts — part two

Only what is new since §9.

### 18.1 CommonJS named exports, and why `tsc` cannot warn you

`exceljs` is CommonJS. Its bundled `.d.ts` declares ES-style named exports, so TypeScript
accepts `import { Workbook } from 'exceljs'` and `tsc --noEmit` passes clean.

At runtime it throws `SyntaxError: The requested module 'exceljs' does not provide an export
named 'Workbook'`. Node cannot ask a CJS module what it exports — the exports object does not
exist until the module runs — so it *statically scans the source* (via cjs-module-lexer) and
guesses. With exceljs it comes up empty.

Measured: the namespace's `.Workbook` is `undefined`; `.default` is the whole `module.exports`
and `.default.Workbook` is the constructor. Fix: default-import plus `esModuleInterop`.

> **A passing typecheck does not mean a CommonJS import works. Run it.**

### 18.2 `as const satisfies` and derived types

`as const` freezes a literal into its narrowest type (`'id'` rather than `string`), so the
array's contents become available *to the type system*. `satisfies` checks the value against a
type **without widening it** — the older `: readonly ColumnDef[]` annotation would have
discarded exactly the literal information that makes derivation possible.

Together they turn a runtime array into a compile-time source of truth.

### 18.3 Crockford base32 and ULID structure

A ULID is 26 characters: 10 encoding a 48-bit millisecond timestamp, 16 of randomness. The
alphabet excludes **I, L, O and U** — the first three because they are misread as 1 and 0, the
last to avoid accidental obscenities. Timestamp-first is what makes ULIDs sort
chronologically as plain strings.

### 18.4 Excel dates, and the 1900 leap-year bug

Excel stores dates as serial numbers counted from 1899-12-30 and deliberately treats 1900 as a
leap year — a bug preserved from Lotus 1-2-3 for compatibility. `exceljs` returns a `Date`, a
`string` or a `number` for the *same column* depending on cell formatting.

The defence is to never store a date as a date: write text cells with `numFmt = '@'`.

### 18.5 Zip determinism

An `.xlsx` is a zip archive, and zip entries carry modification timestamps. Two runs producing
identical content still produce different bytes. Compare workbooks by **entry content**, never
by file hash. See §16.3.

### 18.6 Quirks mode and the srcdoc exemption

No doctype means quirks mode (`document.compatMode === 'BackCompat'`), which changes the box
model. The HTML spec exempts iframe *srcdoc* documents from this rule, so the same markup
parses differently depending on how it was loaded. See §12.

### 18.7 Stacking contexts

z-index only orders siblings **within one stacking context**, so `z-index: 9999` cannot escape
a context that something else paints above. What makes it hard to debug is that the properties
which *create* a context mostly look unrelated to layering — `opacity: .99`, `transform`,
`filter`, `will-change`, `isolation`, `contain`, `position: fixed|sticky`.

A separate trap: `z-index` on a `position: static` element that is not a flex or grid item is
silently ignored.

### 18.8 Small multiples vs spec sheets

Small multiples — the same chart repeated at small scale — suit *continuous, visual* data.
Discrete, enumerable data (a schedule's slots) reads better as a spec-sheet table with aligned
rows, the way phone or car models are compared. Applying the right technique to the wrong data
shape was §5.1's error.

### 18.9 Fitting a camera to content

A perspective camera frames a scene by its bounding sphere: distance = `radius / sin(fov/2)`,
computed against whichever of the vertical or horizontal FOV is tighter, then backed off for
margin. Any hardcoded distance is wrong for some input — too close and you are inside the
geometry, too far and the subject is a speck.
